# 지도·타이틀·상태창의 일본어 — 조사 인수인계

대사·아이템·인명·메뉴는 전부 한글화됐는데 **화면에 일본어가 남는 곳**이 있다.
그 정체를 밝히려던 조사의 기록이다. **아직 안 풀렸다.**

대상:

| 화면 | 예 |
|---|---|
| 지도 지명 | `ゴブリン森`, `クリップス村` |
| 지도 설명문 | `カーティスの都市。帝国とカーティスをつなげる貿易路があり、旅行者達が結構来る。` |
| 스테이지 타이틀 | `王国の遺産` / `グレーのレンジャー` |
| 상태창 스탯 라벨 | `レベル` `経験値` `攻撃力` `防御力` `速さ` `カリスマ` `HP` `MP` |
| FMV 자막 | 오프닝 프롤로그 등 (STR 영상에 구워져 있음 — 별개 문제) |

규모: 스테이지 타이틀 ~30, 지도 지명 수십, 시나리오 설명 ~30 → **100장 안팎.**

---

## 1. 어떻게 했나

### 정적 분석
- `psxtool.py` 로 디스크에서 파일 추출 (`ex/`)
- `mipsdis.py`(자체 제작 MIPS 디스어셈블러)로 EXE 역해석
- `G2DATA1`(76MB)·`G2DATA2`(274MB) 전수 바이트 검색

### 동적 분석
DuckStation 에 **GDB 서버**가 있다는 걸 발견해서 붙였다. WSL 이 Windows
루프백에 직접 못 붙으므로 중계기를 하나 띄웠다.

```
Windows:  python.exe relay.py         # 0.0.0.0:2346 → 127.0.0.1:2345
WSL:      python3 gdbclient.py --host <윈도우IP> --port 2346 info
```

이걸로 한 것:
- RAM 2MB 통째 덤프 (약 47초)
- 무압축 세이브스테이트에서 RAM·VRAM 추출
- **쓰기 워치포인트**로 버퍼에 쓰는 코드 추적 (`watchbuf.py`)

## 2. 검증된 것

### (1) 텍스트가 아니라 이미지다 — 확정

해당 화면이 **떠 있는 상태**에서 RAM 2MB 를 떠서 검색:

| 검색어 | 결과 |
|---|---|
| `カーティスの都市` | **0회** |
| `ゴブリン森` / `クリップス村` | **0회** |
| `貿易路` / `旅行者` / `経験値` | **0회** |

같은 덤프에서 우리가 패치한 한글(`이동`, `장비`)은 정상적으로 잡힌다.
→ 검색 방법 문제가 아니다. **문자열을 폰트로 찍는 방식이 아니다.**

### (2) 비트맵 형태 — 확정

- **4bpp, 폭 208픽셀 (행 간격 `0x68` = 104바이트)**
- 16가지 값을 모두 쓴다
- 값별 마스크를 떠 보면 **글자 픽셀 = 값 0**, 배경 = 1~F
  → **배경 그림 위에 글자를 값 0 으로 뚫은 합성 결과**
- VRAM 에서도 텍스처로 확인됨

### (3) 스테이지 타이틀은 EXE 문자열을 안 쓴다 — 확정

`グレーのレンジャー`(EXE `0x38F8`), `王国の遺産`(EXE `0x390C`)을 한글로 번역해
**디스크에 들어간 것까지 확인**했는데도 화면은 일본어. → 다른 경로다.

### (4) 버퍼에 쓰는 코드 — 확정

정보창 버퍼에 쓰는 것은 **`memset` 과 `memcpy` 뿐**. 별도 글리프 그리기 루프 없음.

| 루틴 | 주소 | 호출자 | 성격 |
|---|---|---|---|
| `memset` | `0x800ACD24`~`0x800ACD50` | `ra=0x80015C58` | 힙 초기화, 크기 `0x10DA8`(약 68KB) |
| `memcpy`(워드) | `0x800A4520`~`0x800A4618` | `ra=0x800A39DC` | **CD 콜백.** 소스 = CD 섹터 버퍼 `0x80123xxx` |
| `memcpy`(바이트) | `0x800ACCE4`~`0x800ACD14` | `ra=0x8009A564` | **게임 코드가 RAM 리소스 블록에서 조각 복사** |

관측 예: `memcpy(dest=0x801E2BBE, src=0x801345AB, len=0x225)`

### (5) CD 읽기 경로 — 확정

```
0x800213D4  씬/스테이지 로더
  lhu  size,[hdr] → malloc(0x80015CA4)
  lw   a0,[0x801251E0]      기준 LBA (이 빌드에선 102,947 = G2DATA1.DAT 선두)
  jal  0x800A38C0           CD 읽기 (a0=LBA, a2=크기, a3=목적지)
  … 스트림을 훑으며 malloc + memcpy 반복

0x800A3A4C  읽기 시작 — LBA→[gp+0x64C], 섹터수→[gp+0x650], 콜백→[gp+0x660]
0x800A39DC  CD 콜백 — 섹터 버퍼 → 목적지 memcpy
```

`gp = 0x80124E08`

| 주소 | 뜻 |
|---|---|
| `[gp+0x630]` | 목적지 포인터 |
| `[gp+0x634]` | 섹터 내 시작 오프셋 |
| `[gp+0x638]` | 남은 바이트 |
| `[gp+0x64C]` | **현재 읽는 LBA** ← 적중 시 읽으면 디스크 위치가 나온다 |
| `[gp+0x650]` | 섹터 수 |

LBA → 파일: `G2DATA1` 102,947 / `G2DATA2` 140,305 / 끝 274,203.
`오프셋 = (LBA - 파일LBA) * 2048`

### (6) 리소스 언팩 루틴 — 부분 확인

```
0x8009A4E0
  malloc(크기)
  [s1+0x38] = 버퍼 (헤더)
  [s1+0x3C] = 버퍼 + count*20   (엔트리 배열)
  memcpy(dest, src, 크기)        ← ra=0x8009A564 로 잡히는 것
  반복: 엔트리마다 포인터를 채우고 s0 += entry.size
  lhu [s1+0x08] = 엔트리 개수 / lhu [s1+0x0A] = 또 다른 개수
```

⚠ 엔트리를 20바이트로 읽었으나 **RAM 에서 그런 배열을 못 찾았다.**
해석이 틀렸을 수 있으니 다시 볼 것.

### (7) 디스크에 무압축으로 있는 것 — 확정

- **지형 타일**: `G2DATA1 + 0x3D60314`, 행 간격 1104바이트
- **RAM 리소스 블록** `0x80134378`~`0x801349D4`(1,628B)
  ← `G2DATA2 0xCE6C7C` 에서 그대로 올라옴 (연속 일치 확인)
  ⚠ 4bpp 렌더하면 글자가 아니라 지형처럼 보임. 정보창 이미지인지 **미확정**

## 4. 반복해서 밟은 함정 — 여기부터 읽어도 됨

1. **힙 버퍼 주소는 세션마다 밀린다.**
   비트맵이 한 세션에선 `0x801E28AA`, 다음 세션에선 `0x801E28DA` 였다.
   지난 세션 주소로 워치포인트를 걸면 비트맵 **바깥**을 감시하게 되어
   무관한 힙 쓰기만 수십 번 잡힌다. **이걸로 두 번 헛돌았다.**
   → 매번 RAM 을 먼저 떠서 현재 주소와 기대값을 구할 것.

2. **스크래치패드(`/tmp/.../scratchpad`)는 주기적으로 비워진다.**
   폴러 스크립트가 사라져 조용히 죽는다. 스크립트·덤프는 리포 안 `dbg/` 에 둘 것.

3. **`HOST=$(...) python3 x.py --host $HOST` 는 빈 값이 넘어간다.**
   쉘이 대입 전에 인자를 전개한다. `H=$(...)` 로 먼저 대입하고 `--host "$H"`.

4. **DuckStation GDB 서버는 `c`(계속)를 받으면 연결을 끊는다.**
   `s`(스텝)는 유지된다. 재개는 **GUI 디버거 F5**, 도구는 `?` 폴링만.

5. **GUI 디버거 브레이크포인트는 실행(Execute) 전용.**
   쓰기 워치포인트는 GDB `Z2` 로만 가능. `Z0`/`Z2`/`Z4` 모두 `OK` 응답.

6. **워치포인트는 GDB 연결이 살아 있는 동안만 유효.** 끊으면 사라진다.

7. `Z2,addr,4` 는 4바이트 범위라 `memset` 이 바이트 단위로 지나가면
   그 4바이트에서 각각 걸린다. 같은 `memset` 이 네 번으로 보인다.

## 5. 도구와 환경

| 도구 | 용도 |
|---|---|
| `gdbclient.py` | GDB 원격 프로토콜 클라이언트 — 레지스터·메모리·브레이크포인트 |
| `relay.py` | Windows TCP 중계 (WSL→Windows 루프백) |
| `watchbuf.py` | RAM 버퍼 쓰기 추적. `memset`·`memcpy` 자동 통과, 소스·크기 기록 |
| `dbg/dump.py` | RAM 2MB 덤프 |

`dbg/` 는 gitignore.

DuckStation 설정 (이미 적용):

```ini
[Debug]
EnableGDBServer = true
GDBServerPort   = 2345
[Main]
SaveStateCompression = Uncompressed
```

경로 `C:\Users\tbfl7\AppData\Local\DuckStation\settings.ini`
(원본 백업 `settings.ini.bak-claude`)

### 세이브스테이트 뜯는 법 (GDB 없이)

무압축 스테이트(약 4MB)에서:

- **RAM 시작**: 패치한 한글 문자열의 EXE 파일 오프셋으로 역산.
  EXE 파일오프셋 `X` → RAM 주소 `0x80010000 + X - 0x800`.
  한 세션에서 `RAM0 = 0x31B58` 이었다. **매번 다시 구할 것.**
- **VRAM**: 파일에서 `GPU-VRAM` 마커 찾아 **+16**, 1MB, 1024×512 16bpp.

## 6. 더 해야 할 것

### 주 경로

1. **게임을 해당 화면(크리프스 마을 지도)에 놓고 RAM 을 뜬다.**
   ```bash
   H=$(ip route | awk '/default/{print $3}')
   python3 dbg/dump.py "$H"        # dbg/ram_map.bin, 약 47초
   ```

2. **현재 세션의 비트맵 주소를 찾는다.**
   값 0 마스크로 폭 208px 렌더를 훑으면 글자 밴드가 보인다.
   찾은 주소가 `BASE`, 행 간격 `0x68`.

3. **글자 밴드 안쪽 주소로 워치포인트를 건다.**
   0 과 비-0 이 섞인 16바이트 창을 골라 기대값으로 삼는다.
   ```bash
   python3 watchbuf.py --host "$H" \
       --watch <BASE+행*0x68+오프셋+4> --probe <같은 자리> \
       --expect <그 16바이트 hex> --outdir dbg
   ```

4. **F5 로 재개 → 마을 들어갔다 나오기 → 멈출 때마다 F5.**
   기대값에 닿으면 `dbg/FOUND_src_*.bin`(원본 4KB)과 호출자 코드가 저장되고 멈춘다.

5. **원본을 디스크와 대조.** `ra=0x8009A564` 경로면 소스는 RAM 리소스 블록이므로
   그 블록을 `G2DATA1`/`G2DATA2` 에서 찾아 파일 오프셋을 확정한다.
   적중 시점의 `[gp+0x64C]`(LBA)도 기록되므로 교차 확인 가능.

### 대안 경로 (위가 막히면 이쪽이 더 나을 수 있음)

**리소스 언팩 루틴 `0x8009A4E0` 에 실행 브레이크포인트**를 걸어 로드되는
리소스를 전수 열거한다. 각 리소스의 RAM 주소·크기와 그때의 LBA 를 모으면
정보창 이미지가 어느 리소스인지 소거법으로 좁혀진다.
`[s1+0x08]`·`[s1+0x0A]`·`[s1+0x3C]` 구조를 실제 값으로 확인하는 것이 먼저다.

## 7. 작업량 판단

원본 형식만 풀리면 **손으로 한 장씩 그릴 일은 아니다.** 글자만 있는 이미지라
한글을 같은 크기로 렌더해 채워 넣는 **도구 작업**이 된다 — 폰트를 교체한 것과
성격이 같다. **형식 해석이 유일한 관문이다.**

FMV 자막은 성격이 다르다. MDEC 영상 재인코딩이 필요하고(`jPSXdec` 등),
재인코딩본이 원래 섹터 수 안에 들어가야 한다. 마지막에 볼 것.
