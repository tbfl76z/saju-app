# 창세기전2 PS1 프로토타입 한글화 — 작업 인수인계

이 폴더는 PS1용 『창세기전2』 미발매 프로토타입(일본판)의 한글화 프로젝트다.
Claude Code 세션은 이 문서를 먼저 읽고 이어서 진행한다.

## 배경

- 창세기전2는 1996년 소프트맥스의 한국 PC 게임. PS1 이식판은 일본 퍼블리셔 VIP와
  준비되어 정식 시리얼까지 받았으나 VIP 파산으로 **발매되지 않았다**.
- 사용자는 당시 소프트맥스에서 이 빌드를 QA 테스트했고, 그 테스트 빌드 이미지를
  보관하고 있다. PC판과는 **대사가 다른 별개 스크립트**다.
- 이 빌드에 **한국어는 한 줄도 없다.** 일본어로 완전히 교체된 상태다. 따라서 이
  프로젝트는 **일본어 → 한국어 완역**이며, 인명·지명은 창세기전 한국어 정식 표기를
  따른다.

## 디스크 이미지 위치 (사용자 PC)

```
D:\g드라이브\창세기전\창세기전\창세기전2-1.BIN   (디스크 1, 677,580,624 bytes)
D:\g드라이브\창세기전\창세기전\창세기전2-2.BIN   (디스크 2, 652,216,656 bytes)
```

WSL(우분투)에서 작업할 때의 경로:

```
/mnt/d/g드라이브/창세기전/창세기전/창세기전2-1.BIN
/mnt/d/g드라이브/창세기전/창세기전/창세기전2-2.BIN
```

같은 폴더에 있는 다른 파일(2026-09-20 `ls`로 확인, 경로 이상 없음):

- `창세기전2-1.iso` (590,002,176), `창세기전2-2.iso` (567,916,544) — 2048바이트/섹터로
  변환한 사본. **작업은 `.BIN`(raw)으로 한다.** 리빌드 검증용 비교 대상으로만 쓴다.
- `창세기전2-2.CUE` — 디스크2 큐시트(`MODE2/2352`, 파일명 인코딩 깨짐). 디스크1 큐는 없음.
- `창세1-1/SLPS02311/EBOOT.PBP`, `창세1-1/SLPS02312/EBOOT.PBP` — PSP용 변환본. 무시.

`/mnt/d`는 Windows의 D: 드라이브다. 파일명은 먼저 `ls`로 확인한다. `/mnt/d` 읽기는
WSL 파일시스템보다 느리므로, 추출 결과(`ex/`)는 리포 안(리눅스 쪽)에 둔다.

구글 드라이브 동기화 폴더일 수 있다. 작업 산출물(추출 파일 등)은 이 폴더가
아니라 리포 안의 `ex/` 같은 곳에 둔다. `.gitignore`가 막고 있으니 커밋되지 않는다.

## 이미 확인된 구조 (두 디스크 모두 검사 완료)

| 항목 | 내용 |
|---|---|
| 형식 | MODE2/FORM1 raw, 2352 bytes/sector, 데이터 오프셋 24 |
| 시리얼 | 디스크1 `SLPS_023.11`, 디스크2 `SLPS_023.12` |
| `G2DATA1.DAT` | 76,509,184 bytes. **일본어 스크립트 전체가 여기.** Shift-JIS 평문, 7,321개 덩어리 |
| `G2DATA2.DAT` | 274,221,154 bytes. 텍스트 0건 → 그래픽·사운드 |
| `SLPS_023.11` | 1,138,688 bytes. 실행파일. 시스템 메시지 133건. **디스크 1에만 있음** |
| `XA/`, `XA3/` | STR 동영상·XA 음성. 디스크 간에 다른 건 이것뿐 |
| 두 디스크 관계 | `G2DATA1.DAT`, `G2DATA2.DAT`는 파일 내 오프셋까지 **완전히 동일** |

결론: **`G2DATA1.DAT` 하나를 한글화해서 두 디스크에 같이 넣으면 된다.** 코드 수정은
디스크 1의 실행파일 하나.

알려진 좌표:
- `G2DATA1.DAT+0x75874C` — 90글자짜리 대사 덩어리. 제어 코드 분석 출발점
- `G2DATA1.DAT+0x33ED697` 부근 — `0xB8` 채움 데이터 (한글 오탐 원인, 무시)
- 디스크2 절대 오프셋 `0x0A7F76C0` 부근 — 가타카나 인명 테이블, 고정 길이 레코드로 보임

## 2026-09-20 세션에서 확인한 것 (1~5단계 완료)

추출은 `ex/`에 되어 있다(디스크 1 전체 30개 파일). 아래는 전부 `ex/` 기준.

### G2DATA1.DAT 인덱스 — EXE 안에 있다

- EXE 파일 오프셋 `0xC1AF8~0xC4448` (RAM `0x800D12F8`), **u32 바이트 오프셋 배열, `FF FF FF FF`로
  구분된 60개 그룹, 총 2,523 엔트리**. 그룹 사이에 수 KB~185KB 공백(그룹 마지막 엔트리의 실제 크기).
- `ex/g2data1_index.tsv` (group, idx, offset, size)로 저장해 둠. 없으면 이 문서의 좌표로 재생성.
- G2DATA1.DAT 자체에는 헤더가 없다. 파일 선두가 바로 캐릭터 테이블.

### 텍스트가 있는 곳

| 위치 (G2DATA1) | 내용 | 구조 |
|---|---|---|
| `0x0` ~ 약 `0x8000` | **캐릭터 테이블** (イオリン=이올린, レイシッド, デュラン…) | 256바이트 레코드: +0 짧은 이름(24B), +24 긴 이름(24B), +0x78 스탯 |
| `0xC464`~ | 직업 설명 | NUL 종결, 4바이트 정렬 |
| `0xE7AC`~ | **아이템 테이블** (S.T.S, 魔法の盾, 火の盾, レッドネックレス…) | 68바이트 레코드, +0 이름 |
| `0xEFE8`~ | 아이템 설명 | NUL 종결 |
| `0x11EBC`~ | 마을 NPC 대사 | NUL 종결 |
| `0x8C0000`~`0x1810000` | **스토리 대사 본체** (7,679 문자열) | 아래 "텍스트 섹션" 형식 |
| EXE `SLPS_023.11` | 시스템 메시지, **마법 이름**(ダーク・ゾーン…), 메뉴(ターン終了/ＴＰタメ/ステータス), 선택지 | NUL 종결 SJIS, RAM 포인터로 참조. `ex/SLPS_023.11.tsv` |

### 텍스트 섹션 형식 (스토리 대사) — 포인터 테이블 찾음

각 스크립트 블록(인덱스 엔트리, 예: 그룹 `0xC1F1C` #340 = `[0x744F48, 0x780238)`) 안에
텍스트 섹션이 들어 있고, 형식은:

```
u32 count          ; 레코드 수
u32 size           ; 섹션 전체 크기 (count 필드부터 마지막 레코드 끝까지)
u32 offs[count]    ; 각 레코드의 상대 오프셋 (기준 = offs 배열 바로 뒤 = 첫 레코드)
레코드 × count:
  u32 len          ; 본문 바이트 수 (NUL 제외)
  u8  text[len]    ; Shift-JIS
  u8  0            ; NUL, 이후 4바이트 정렬 패딩
```

검증: 0x744F48 블록의 섹션(블록 상대 `0x12A20`) count=45, offs 45/45 일치, 주 대사 구역의
`/5` 문자열 703개 모두 len 필드 == 실제 길이. **레코드 길이가 바뀌면 len·offs·size를
재계산하면 된다.** 단, 섹션 뒤에 다른 데이터가 이어지므로 섹션이 커지면 블록 전체와
EXE 인덱스(뒤 엔트리 전부)를 밀어야 한다. 블록 안에서 이 섹션을 가리키는 값은 아직
못 찾았다(u32/u16, 절대/상대 모두 0건) → 블록 헤더(선두 u16 ID 열) 해석이 남은 과제.

제어 코드는 **ASCII 이스케이프**: `/5`(화자명 시작, 색), `/1`(본문 복귀), `/n`(줄바꿈),
`/s3`(선택지 구분?). 바이너리 제어 코드 없음.

### 폰트 — EXE 안, 표준 TIM 아님 (timtool 결과 7개는 전부 오탐)

| 항목 | 값 |
|---|---|
| 형식 | **1bpp, 16×13 픽셀, 글리프당 26바이트**(13행 × u16 big-endian 비트열) |
| 비한자 | RAM `0x800DFBDC` (파일 `0xD03DC`), 524자 — 기호·숫자·라틴·히라가나·가타카나·그리스·키릴·선문자 |
| 1수준 한자 | RAM `0x800E3114`, 2,965자 (JIS 순서 亜唖娃…) |
| 2수준 한자 | RAM `0x800F5E38` ~ `0x8010B684`, 3,390자 |
| 합계 | 6,879 글리프, 178,854바이트 |
| 렌더링 | **가변폭**. 글리프의 좌우 빈 열을 찾아 실제 폭 + 4px 로 진행. 빈 글리프는 8px |

렌더러 코드:
- `0x80019A50` **SJIS → 글리프 인덱스 + 그리기**. a0=선두 바이트, a1=후속 바이트.
  세 구간(0x8140~0x84BE 비한자 / 0x889F~0x9872 한자1 / 0x989F~0xEAA4 한자2)을
  (빼기, 더하기) u16 쌍 리맵 테이블 `0x800DFA7C`(19쌍) / `0x800DFAC8`(32쌍) /
  `0x800DFB48`(37쌍)로 압축 인덱스로 바꾸고, `인덱스×26`을 폰트 베이스에 더한다.
- 폰트 베이스 포인터 3개는 `gp+0x438/0x43C/0x440` (`gp=0x80124E08` → `0x80125240..48`),
  `0x80019404`에서 상수로 설정.
- 글리프는 `0x80153F90 + (a2>>1)`의 8bpp 소프트웨어 버퍼(행 stride 0x80)에 색
  `gp+0x444/0x445`로 찍힌다. 그 뒤 VRAM으로 올리는 코드는 아직 안 봤다.

확인 명령: `python3 tileview.py ex/SLPS_023.11 0xD03DC out.png --bpp 1 --tile 16x13 --count 524`

### 한글 폰트 전략 (6단계 권장안)

렌더러를 건드리지 않는 **코드 치환** 방식이 가능하다:
1. 한글 완성형 2,350자 + 필요한 기호를 **쓰지 않을 JIS 한자 코드**(2수준 3,390슬롯이면 충분)에
   1:1로 배정하는 대응표를 만든다.
2. 번역문을 그 대응표로 SJIS 바이트열로 인코딩해 넣는다(게임은 그냥 한자로 인식).
3. 해당 슬롯의 26바이트 글리프를 한글 16×13 비트맵으로 바꾼다 (EXE 안, 위치 고정).
가변폭 렌더러라 한글 폭(대개 12~14px)도 자연히 맞는다. 13px 높이가 빡빡하므로
12px 계열 한글 비트맵 폰트(둥근모꼴 등, 라이선스 확인)를 후보로.

| 도구 | 용도 |

| `timtool.py scan/extract` | TIM 이미지 탐색, PNG 변환 (폰트 찾기) |

| `tileview.py` | 헤더 없는 원시 비트맵/타일을 PNG로 (폰트 확인용, `--bpp 1 --tile 16x13`) |

사용법은 `README.md`. 새 도구를 만들 때도 같은 원칙: 단일 파일, 표준 라이브러리만,
한국어 도움말, 합성 데이터로 검증 후 커밋.

## 작업 순서

1~5는 끝났다(위 섹션). 남은 것:

6. **한글 폰트 전략 확정**: 위 권장안(코드 치환)으로 갈지 결정. 확정되면 (a) 한글↔JIS 슬롯
   대응표 생성 도구, (b) 16×13 한글 비트맵 → 26바이트 글리프 변환 도구, (c) EXE 폰트 패치.
   추가로 볼 것: `0x80153F90` 버퍼를 VRAM으로 올리는 코드(글자 캐시 크기 제한 여부),
   메뉴/이름처럼 EXE·테이블에 고정 길이로 박힌 문자열의 폭 제한.
7. **재삽입 파이프라인**: 번역 TSV → 대응표 인코딩 → 텍스트 섹션(len/offs/size) 재조립 →
   블록·EXE 인덱스 재계산 → `G2DATA1.DAT` 재조립. 먼저 캐릭터/아이템 테이블(고정 길이라
   인덱스 재계산 불필요)과 EXE 문자열로 화면 검증.
8. **리빌드**: `mkpsxiso`로 ISO 재생성, 두 디스크 모두. xdelta 패치로 배포.
9. **검증**: DuckStation으로 실행. 사용자가 화면을 확인한다.

## 범위 (사용자와 합의 필요, 권장안)

먼저 **메뉴·인명·아이템·마법명**만 한글화해서 폰트 렌더러가 실제로 한글을 찍는지
검증한다. 그 다음 스토리 대사 완역. 폰트가 이 프로젝트의 성패를 가르므로 짧은
문자열로 먼저 뚫는다.

## 주의

- 디스크 이미지, 추출 파일, 덤프 TSV는 **절대 커밋하지 않는다** (`.gitignore` 참고).
- 배포물은 ISO가 아니라 **xdelta 패치**. 원본 디스크 보유 전제.
- 게임 대사를 분석에 필요한 만큼만 다룬다. 로그·문서에 스크립트를 통째로 옮기지 않는다.
- 도구 출력과 커밋 메시지는 한국어.
